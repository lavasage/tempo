| 4 | 评分能描述单节感受，无法比较动作进步 | 未实现 | 评分/用力/时长/备注仍是唯一训练记录；动作、组次、重量属于客户端新模型，需单独一批 |

### 第 3 项的语义边界

- 队列是「至少一次」：重放依赖幂等键。预约创建已用课程 id 作 `p_request`，状态变更与 upsert 天然可重放，所以不会产生重复课程。
- 仍未做「按请求 id 查询结果」的接口：极端情况下服务端成功但响应丢失，界面会显示待同步直到下一次重放成功。对当前单教练场景可接受；接入套餐扣课时必须补结果查询，否则余额可能显示滞后。

## 下一步

套餐课时闭环（评审 P0）已具备前提：可靠提交先落地了。建议按 `docs/REVIEW_IMPLEMENTATION.md` 第二批顺序推进：

1. 套餐/流水/预约归属模型与兼容读取；
2. 本地原子快照服务与边界测试；
3. 服务端事务（完成与扣减同一事务、预约 id 幂等、套餐级锁）；
4. 学员档案套餐卡 → 排课匹配 → 完成扣课与流水 → 带原因冲正。

移动整合剩余项（样式层叠合并、其他短操作接入、实机键盘/原生返回）不阻塞套餐，可与套餐并行排在后面。
